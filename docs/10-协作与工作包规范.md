# 10 协作与工作包规范

> 版本：v2.0 · 2026-11-02 · 状态：已定稿
> 多个 agent（和人）并行开发时遵守的协议，以及工作包必须写到什么程度。术语见 [00](00-术语与约定.md)，平台分工见 [ADR-016](decisions.md)，看板见 [wp/README.md](wp/README.md)。

## 1. 总则

1. **一个工作包 = 一个分支 = 一次评审 = 一次合并。** 工作包文件是执行合同：里面写的就是要做的，没写的就不做。
2. **不确定就停下来写变更申请，不要猜。** 文档有歧义、做不到、需要新依赖、需要改接口，一律走第 8 节。
3. **只改自己的文件。** 工作包头部的 `owns` 是你独占的路径；`appends` 是只能追加的共享文件；其余路径只读。
4. **测试先行。** 先写工作包第 8 节列出的测试，看到它们失败，再实现。
5. **平台差异只放平台层。** 见 [ADR-016](decisions.md)。
6. **每个工作包要能被人在 15 分钟内评完。** 规模上限：MVP-0 的工作包代码加测试不超过 800 行，超过就拆。

通用规则（每个实现者都必须遵守）：

| # | 规则 |
|---|---|
| 1 | 先读后写：先读 [00](00-术语与约定.md)、工作包文件、工作包第 2 节列出的文档小节。**不要通读全部文档** |
| 2 | 禁止臆造外部接口。没有亲自核实的字段、端点、费率，写成 `TODO-VERIFY(<工作包ID>)`，并在对应探针工作包里核实 |
| 3 | 不引入未批准的依赖；不改 `pyproject.toml`、`package.json`、`Cargo.toml` 里的依赖（WP-00 已装齐，见 [02](02-技术架构.md) 第 4 节） |
| 4 | 不写死密钥、路径、模型名。全部走配置与环境变量；密钥永远不进日志、数据库、测试数据 |
| 5 | 不静默失败。捕获异常必须映射到 [05](05-接口契约.md) 的错误码，并写结构化日志 |
| 6 | 用户可见文案放 `messages/<域>.py`（后端）或 `i18n/zh-CN/<页面>.ts`（前端），不散落在逻辑里 |
| 7 | 不使用本机当前时间做业务判断，一律用 `clock.now()` |
| 8 | 诚实标注：缓存数据、仅标题、整段证据、引擎降级，界面上必须可见 |
| 9 | 提交信息 `type(scope): summary`，见 [00](00-术语与约定.md)。小步提交，每个提交都应能通过 `scripts/check.*` |
| 10 | 不要执行 `git push`、`git merge`、`git rebase` 到 `main`，也不要改别人的分支。合并只由协调者做 |

## 2. 角色

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 协调者 | 按看板派发工作包；合并通过评审的分支；处理变更申请；维护 `wp/README.md` 的看板；每次合并后在 `main` 上跑 `scripts/check.*` | 不写工作包范围内的业务代码 |
| 实现者 | 领一个就绪的工作包，在独立的 worktree 里完成 | 不改 owns 之外的文件；不自行决定歧义 |
| 评审者 | 按第 7 节的清单评审一个分支，给出“通过 / 退回 + 原因” | 不直接改被评审的分支 |
| Windows 实现者 | 同实现者，但只领 `platform: windows` 的工作包，并按第 9 节的协议维护 Windows 兼容性矩阵 | 不为 Windows 修改共享接口 |

## 3. 工作流

仓库当前没有任何提交。**协调者先做一次初始提交**（`docs/`、`contracts/`、`design/`、`scripts/`），建立 `main` 分支，之后才能创建 worktree。

```text
1. 协调者在 wp/README.md 把工作包标为 doing，并写上负责人
2. 实现者：  git worktree add ../wt-<ID> -b wp/<ID> main
             cd ../wt-<ID> && scripts/setup.sh        （Windows：scripts\setup.ps1）
3. 读：       00 + 工作包文件 + 工作包第 2 节列出的小节
4. 写测试：   按工作包第 8 节，运行，确认失败（把失败输出贴进状态文件）
5. 实现：     按工作包第 6 节，直到第 9 节的验收命令全部通过
6. 自检：     scripts/check.sh（Windows：scripts\check.ps1）全绿
7. 写状态文件： docs/wp/status/<ID>.md（模板见第 6 节）
8. 提交并通知协调者
9. 评审者按第 7 节评审 → 协调者合并（git merge --no-ff）→ 看板标为 done
```

**并行度**：看板上所有依赖都已 `done` 的工作包是“就绪”的，可以同时派发。同一时间每条车道建议不超过 2 个进行中的工作包。

## 4. 工作包文件

位置：`docs/wp/mvp0/<ID>-<ascii-slug>.md` 或 `docs/wp/v1/…`。文件名必须以 ID 开头，slug 只用小写字母、数字、连字符（例：`C-03-storage.md`）。

### 4.1 头部字段

头部用 YAML 子集：单行 `key: value` 或 `key: [a, b]`，`scripts/check_docs.py` 会检查。

| 字段 | 必填 | 取值与含义 |
|---|---|---|
| `id` | 是 | 如 `C-03`，全仓库唯一 |
| `title` | 是 | 一句话中文标题 |
| `phase` | 是 | `mvp0` 或 `v1`；必须与所在目录同名；mvp0 的工作包不得依赖 v1 的 |
| `platform` | 是 | `shared`、`macos`、`windows`（见 [00](00-术语与约定.md) 3.4） |
| `lane` | 是 | `core` `data` `semantic` `ui` `integration` `windows`；`windows` 与 `platform: windows` 互为充要条件 |
| `deps` | 是 | 依赖的工作包 ID 列表，可为空 `[]`。`shared`/`macos` 不得依赖 `windows` |
| `size` | 是 | `S`（< 300 行）、`M`（300–800 行）；v1 可用 `L`（> 800 行） |
| `owns` | 是 | 独占的路径列表。目录以 `/` 结尾。任意两个工作包的 `owns` 不得重叠 |
| `appends` | 否 | 只许追加的共享文件。每个文件必须被某个工作包的 `owns` 覆盖，且追加方要（传递）依赖拥有方 |
| `stubs` | 否 | 本工作包创建的占位文件，由另一个工作包接手。占位文件不得出现在自己的 `owns`；接手方必须在 `owns` 里覆盖它，并依赖本工作包 |

`stubs` 的用途：骨架工作包（WP-00）必须在第一天创建 `platform-windows.css`、`windows.rs` 这类文件，否则项目编译不过；但它们最终归 Windows 车道所有。WP-00 先建好占位内容，由 `W-xx` 接手。

### 4.2 详细程度门槛（评审时逐条核对，任何一条不满足就退回）

工作包的目标是“实现者不需要再做任何设计决定”。

| # | 门槛 |
|---|---|
| D1 | 每个要创建或修改的文件都有**路径**和**一句话职责**（第 4 节） |
| D2 | 每个公开函数 / 类 / RPC 处理器都有**完整签名**：参数名与类型、返回类型、会抛出的错误（第 5.1 节） |
| D3 | 每个数据结构都有**字段表**：名称、类型、是否必填、取值约束、含义（第 5.2 节） |
| D4 | 每个算法都有**可执行的步骤或伪代码**，涉及的常量写出确切数值。禁止出现“适当”“按需”“视情况”“等” |
| D5 | 每个错误和边界情形都有**明确行为**与错误码，包括用户看到的中文文案或其所在的 messages 键（第 7 节） |
| D6 | 每个测试都有**名称、输入、期望值**，期望值是具体的数字或字符串，不是“应该正确”（第 8.1 节） |
| D7 | 需要的 fixture 写明**路径、内容来源、怎么录制或构造**（第 8.2 节） |
| D8 | 验收命令**可原样复制执行**，并写出期望输出里的关键行（第 9.1 节） |
| D9 | 引用其他文档时**链接到具体小节**，不是只写文件名 |
| D10 | 没有悬空的 `TODO`。外部事实标 `TODO-VERIFY(<ID>)`，且 `<ID>` 是一个真实存在、会去核实它的工作包 |

## 8. 变更申请（CR）

文档与实现冲突、文档有歧义、需要新依赖、需要改契约时，**停下手上的工作**，在 `docs/wp/cr/` 新建 `CR-<YYYYMMDD>-<简述>.md`：

````markdown
# CR-<日期>-<简述>

- 提出者（工作包 ID）：
- 类型：文档错误 / 做不到 / 需要新依赖 / 接口变更 / 平台问题
- 现象：（发生了什么，附命令输出）
- 依据：（链接到文档小节）
- 方案：（至少两个，各写影响面）
- 阻塞的工作包：
- 决定：（协调者填写：采纳方案 X / 驳回，及原因；日期）
````

协调者批准后，**先改文档和契约，再改代码**。被驳回的申请保留，不删除。

## 9. Windows 车道协议

Windows 的一个人遵守第 1–8 节的全部规则，另外：

1. **起点**：WP-00 已合并到 `main`。ADR-021 仅解禁 W-00；W-01～W-05 必须等协调者审阅 W-00 后逐包恢复。
2. **第一件事**：W-00（环境摸底）。由于 `.ps1` 仍是占位，先在 Windows 上直接运行 `python scripts\doctor.py`、`python scripts\setup.py`、`python scripts\check.py`，把每个失败项原样记进 `docs/wp/status/W-00.md`。不要修改任何产品代码或 `.ps1`。
3. **持续对等**：Mac 一侧每合并一个 `platform: shared` 的工作包，Windows 实现者应在**一个工作日内**拉取新的 `main`，运行 `scripts\check.ps1`，把结果更新到 `docs/wp/windows-matrix.md`（每个共享工作包一行：通过 / 失败 / 未验证，失败要写原因和对应的变更申请或修复分支）。
4. **发现共享代码在 Windows 上有问题时**（[ADR-016](decisions.md) 第 5 条）：
   - 能在平台层解决的，在 `W-xx` 的 `owns` 里解决；
   - 必须改共享代码的，分支名 `wp/W-fix-<简述>`，只含**最小修复加一个能复现问题的测试**，并在 `docs/wp/cr/` 提一个“平台问题”类变更申请，由共享代码所属车道的人评审；
   - **不得为 Windows 修改共享接口**（RPC 方法、契约、数据表、公开函数签名）。需要改接口走变更申请。
5. **不阻塞 Mac**：Windows 的任何失败都不阻止 Mac 合并。看板上 Mac 工作包的 `done` 不依赖 Windows 验证。
6. **验收独立记录**：Windows 的 MVP-0 验收见 [01](01-产品需求.md) 第 8 节“Windows 车道的 MVP-0 验收”，结论写进 `docs/wp/status/` 下对应的 W 工作包状态文件。

## 11. Definition of Done

每个工作包合并前必须满足：
