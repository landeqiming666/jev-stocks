## 60 秒与取消的实际语义

每个已获得槽位的逻辑请求从 monotonic 开始计时，60 秒覆盖首次 SDK 尝试、
SDK 自有三次额外 retry、退避、读流/解析以及可能的一次上下文拆分；不是每次
retry 重新获得 60 秒。SDK RetryPolicy.timeout=60/max_retries=3，仍是唯一瞬态
重试层；SDK 会在下次退避超预算时提前抛回原错误。使用锁定 0.7.5 的
`TypeSafeClient._retry.sleep` seam 将 SDK 退避改成 Event 阻塞等待和取消检查，
没有业务外 5xx retry。transport 每次发送和流块前后检查同一截止并缩短操作 timeout。

每引擎最多 max_workers（严格 int 1..4）个 daemon 调用槽；没有 ThreadPoolExecutor
或无界排队请求。消费者以 Condition 等待，最多 20 ms 复查结构 CancelToken，
不是 sleep busy-loop。任一失败/取消/截止设置本批 stop，立即停止后续派发及 SDK
退避/发送，丢弃结果。等待旧卡住槽位的新批次有独立最多 60 秒 capacity deadline。
多段落批次可以超过 60 秒；60 秒是每个逻辑请求的预算，非整个扫描的总时限。

SDK in-flight 的系统阻塞无法安全强杀线程：消费者已返回时线程可能仍活着且
继续占用本引擎槽位，后续批次不会通过新建线程绕过 4 路上限。返回后若旧 transport
解除阻塞，会在 guard 处发现 stop/cancel/deadline，不发额外 retry。子进程测试用
真实 SDK + 永久阻塞 MockTransport，取消后能正常 exit；不是声称远端请求已被撤回
或不会产生计费。没有证明 OS 网络栈硬中断、真实公网时延或响应体积上限。
