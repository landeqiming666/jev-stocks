## 实现与消费方式

公开 API 为 `load`、`health`、`close`、`score_pairs`、`score_event`、`locate_evidence`，
加两个 SQL builder 和 `map_jevdb_error`。返回 S-02 的 Probabilities/PairScore/EvidenceScore，
接口满足 SemanticEngine；模型只接受固定 `jev-x.y.z`，不接受 latest。

专用 `:memory:` 连接，校验 DuckDB 1.4.3、绝对存在的扩展路径与后缀，拒绝引号、
NUL、CR/LF，支持空格/中文。路径来自明确构造配置，不从 RPC 读取，不连接主库。
模型和完整 HTTPS endpoint 通过绑定 SET，沿用 G0 的 `/v1/systemone` 到 `/v1/` 规则；
拒绝 userinfo、query/fragment、非法主机/端口及不匹配路径。gateway key 只发配置的端点。
显式构造参数 `endpoint` 优先；构造根负责读取其当前配置，模块不读取或猜测 gateway 环境。

`load()` 无 key 也可成功，不创建 secret；`health()` 返回 unconfigured，评分返回
CONFIG_REQUIRED 且 `missing=[jevKey]`。每次评分重新消费 secret_provider 的当前 key，
支持下一次调用使用新配置。连接仅持有临时 secret，不保存 key 字符串到实例或 SQL；
有效 provider key 在返回后立即 register_secret，health/评分/证据均覆盖，纯 provider
且未通过 SecretsService/env 登记的 key 也受进程统一日志脱敏保护。
provider 抛 SentinelError 时保留原错误族/码、消息键、retryable 与脱敏后的诊断字段，
离开 except 后抛新错误对象，health 路径也不保存原始异常链；SecretsService 的钥匙串
故障保持 INTERNAL 和 settings.keyring_unavailable，不误报 CONFIG_REQUIRED。
未知 provider 异常映射 INTERNAL/SECRET_PROVIDER_FAILED；只有缺值/无效值或明确
CONFIG_REQUIRED 才按缺 key 处理。真实 SecretsService 加 synthetic 故障 store 回归覆盖三条 API。
创建 secret 的短窗口受 `_ENV_LOCK` 保护，随后恢复原环境，查询 finally 清理 secret。
禁用正文/raw dump 和 cascade，`on_error=error`，不静默直连；自动降级由 S-02 selector 处理。
SENTINEL_OFFLINE 在 secret 前、SQL 前都检查，运行中转离线的回归不执行模型查询。

th/ps 去重，wanted 只插请求组合，MATERIALIZED CTE 在概率投影前约束实体对。
真实 DuckDB 加 synthetic 有副作用 UDF 的单测证明：3 个请求对仅调用 14 个概率，
不会评分未请求的第四对。重复请求对恢复原始顺序和返回数量，不重复概率 SQL。
同身份不同内容明确拒绝；缺行、重复行、额外行、NULL、bool、NaN、越界均整批 MODEL_ERROR。
kill_condition 只进入 kill_met STRUCT，无 kill 时 kill 概率为 NULL；有 kill 时 NULL 是错误。
证据用 S-02 独立 JEVDB 模板，按 s1..sN 恢复顺序，不返回用户句子，不计算字符偏移。
所有用户文字只经 executemany 参数传入。没有复制上游全文或修改问题文字/版本/阈值。

token 为 S-02 estimate_tokens 的字符估算，计入本次实际调用的 instructions，
固定 tokens_estimated=True，同批复用评分 SQL 墙钟 latency；不声称实际 usage。
stats 只记录数值/NULL，不记录响应正文；统计失败不改变评分成功结果。
401/403、429、超时与其他模型错误分类独立；Retry-After 未暴露时显示规定默认 30 秒。
map_jevdb_error 返回 SentinelError；400/413/422 非上下文错误映射
InternalError(reason=INVALID_REQUEST)，优先于错误正文里的 timeout 字样。
错误不发布远端 body，存入调用槽前删除异常 cause/context/traceback，避免实例保留 raw key。

## 串行、取消与清理边界

公开生命周期由 RLock 串行；唯一 daemon 调用槽持有连接，整个评分的加载、环境等待、
临时表、原生 SQL、stats、映射和 finally 都在槽内。总预算默认 60 秒，包含排队等待；
控制线程轮询 CancelToken，取消/超时对本次连接 interrupt 一次并丢弃结果。
等待另一个调用的取消不会 interrupt 正在执行的调用。

原生 C++ 的 timeout 是读写超时、连接超时另为 30 秒，并非总预算。
Python 60 秒限制是调用者等待上限加至多一次 20ms 检查间隔，不保证 OS 硬实时。
无法强杀原生线程或撤回远端请求；旧查询/清理未结束时保留唯一槽位，禁止新建线程或
并发复用连接规避阻塞。该状态的新请求有界等待后 TIMEOUT；完成清理后才允许再用。
close 对在途任务请求 interrupt 并让原 worker 清理；普通 native close 也在有界等待槽内。
若 close 超时，实例已进入关闭状态，原槽继续清理，调用方不可再用该实例。

th/ps/wanted/ev 与 secret 全部 finally DROP；部分建表失败也逐表尝试清理。
清理失败整批报错并关闭专用连接，禁止返回“成功且残留临时表”。
原生 HTTP 卡住时 secret/临时表仅能在旧查询退出后清理，这是实测范围之外的限制；
本地 CPU interrupt 与 synthetic 不可中断查询的占槽回归分别验收，不混称 HTTP 取消已验证。
