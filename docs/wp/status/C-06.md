## 规范矛盾与具体处理建议

以下差异已经在实现过程及时报告，保留原示例，没有静默修改数值、文字、字段顺序或场景名。当前可审阅实现采用明确且受测试限制的兼容处理；协调者应在集成前确认并提交规范修订。

1. **方法生成顺序**：05 §5.10 与 C-06 §5.4 要求 `app.ping → app.bootstrap → app.shutdown`；现有 author EX 和 mock 字节是 `app.ping → app.shutdown → app.bootstrap`。`index.methods` 保留 05 正式顺序；生成器仅对这两个生命周期方法恢复现有 mock 顺序。建议修订 C-06 §5.4，明确历史输出顺序；后续若允许统一顺序，协调者需同时重新生成原型与审查该变更。
2. **生成第二行**：现有文件第二行是 `window.MOCK = {`，没有独立的 `window.MOCK = ` 行。生成器保持现有字节、UTF-8/LF/无 BOM、固定头注释和末尾 `;\n`。建议将规格文本说明改为同一行拼接。
3. **分页字段缺失**：`scan.history/{default,empty,budget_exhausted,running}` 与 `paper.orders/default` 共 5 个成功示例缺少 05 §5.6–§5.7 要求的 `nextCursor`。正式 result schema 仍要求该字段，公开 `validate()` 会拒绝这些原始结果；仅整个示例目录检查对这 5 个固定名称允许缺失 `result.nextCursor`。字段出现时仍验证类型。建议协调者为这 5 个源示例补 `nextCursor:null` 并重新生成 mock 后删除兼容清单。
4. **拒单订单 ID 缺失**：`paper.order.place/{insufficient_cash,insufficient_position}` 两个错误都缺少 05 §3.2、§5.7 的 `data.orderId`。`RpcError` 的 `ORDER_REJECTED` 变体仍强制要求 `orderId` 和 `reason`；公开 `validate()` 会拒绝原始错误，仅目录检查对这两个固定场景允许该字段缺失。建议协调者先确定对应已保存 rejected 订单的虚构 ID，再修正 author 源示例和 mock，随后删除兼容清单。
5. **故意无效的参数**：09 §4 与 C-06 §6 泛指所有示例参数通过 schema，但已有 `negative`、`empty`、`too_long`、`invalid_email` 明确是参数校验失败示例。正式参数 schema 保持非负、非空、长度与邮箱约束；目录检查只对 `INVALID_ARGUMENT` 且 `data.field` 精确指向实际无效的已声明字段允许该字段失败，其余字段及未知字段仍检查。业务性 `limit_reached` 的合法参数正常验证。建议修订 09 §4，区别参数校验失败示例与成功/业务错误示例。
6. **可空动作备注**：05 §5.5 的简表写 `note?:string`，但 `decision.act/still_valid` 参数为 `note:null`，公共 `ActionRecord` 与 P-03 §5.2 的备注明确可空且最多 200 码点。按公共类型与 P-03 建立 `string|null` schema。建议同步简表。
7. **错误列不穷举传输/引擎错误**：author 源为补齐 15 错误码给 `instruments.search` 加 `CANCELLED`，给 `scan.start` 加 `RATE_LIMITED/UNAUTHENTICATED/ENGINE_UNAVAILABLE`，给 `scan.retryBatch` 加 `TIMEOUT/INTERNAL`。方法 errors 清单包含这些实际场景和 05 的业务错误，且 `scan.start` 包含正文要求的 `INVALID_ARGUMENT`。建议说明 05 方法表的错误列只列业务错误，补充通用错误的适用规则。
8. **结果多余字段**：05 §11 规则 1 说结果允许多余字段，而 C-06 §6 步骤 2 明确所有对象 `additionalProperties:false`。本任务遵循用户要求的真实严格 schema 与 C-06 约束，结果和嵌套对象也闭合；建议统一 05 §11 的说明。

七个缺字段兼容例外仅作用于目录中命名的旧示例，不改变任何 schema，也不补写示例值；重命名场景、提供错误类型的 cursor/orderId、删除 retryable、未知字段仍失败。回归测试同时直接调用公开 schema 校验，证明分页和拒单字段的必填约束仍存在。

## 实际接口与工作包 5.1 的差异

- 三条要求命令原样可用。两个脚本增加符合 `scripts/check.py` 占位调用的默认绝对仓库路径，所以直接 `--check` 可以运行。
- `--check` 缺输出或首个字节差异退出 1，并打印首个差异行；不创建目录、不写文件。
- 输出路径在 contracts 内时，无论生成或检查均退出 2。
- `check_contracts.py` 提供 `check_contracts(path)`、`check_schema(schema,types,path)`、`validate(value,schema,types,path)`、`load_json(path)`；校验失败抛 `ContractError`，CLI 输出字段路径并退出 1。
- 支持 `$ref`、闭合对象、数组、required、type/可空类型、enum/const、长度、pattern、日期格式、数值边界、anyOf/oneOf/allOf 和 uniqueItems。引用只接受根目录 `types.schema.json#/$defs/...` 或 `#/$defs/...`，支持 JSON Pointer 转义；拒绝网络引用、循环引用、未知关键字与未使用定义中的无效 schema。
