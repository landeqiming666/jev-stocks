## DuckDB 1.4.3 实证与文档矛盾

1. **C-03 §5.1 的 cursor 事务描述不成立。** 原生 `connection.cursor()` 使用独立事务，不与主连接/其他 cursor 共享未提交数据。真实测试 `test_real_duckdb_cursor_transaction_is_independent`：writer BEGIN 后插入 1，writer SELECT 得到 `[(1,)]`，另一 cursor SELECT 得到 `[]`，ROLLBACK 后无行。按用户要求保留每个上下文独立 cursor；因此 write 内的 `db.read()` 返回独立的已提交快照，不能兑现“看到自己的未提交写”。需要读取事务内数据的下游应将 `tx` 作为 SqlExecutor 传给只读函数。没有复用同一个 cursor 假装独立，也没有跳过这个检查。

2. **C-03 §5.1 的 WriteTx.execute 原生返回类型带有逃逸能力。** 保留了指定的 `duckdb.DuckDBPyConnection` 返回签名，保护的是 `tx.execute/tx.executemany` 与 Database 上下文入口。原生返回对象自身还提供 execute/commit/rollback；直接在该对象调用这些方法可绕过包装层。原生连接 execute 属性不可覆写，直接子类代理也不能安全初始化。若“禁止事务边界逃逸”包括这个公开返回对象，主 agent 需要把返回契约收紧为受保护的 SqlExecutor/WriteTx，或者明确返回对象只供 fetch；本包没有通过类型伪装或动态导入掩盖此限制。

3. **备份新旧排序。** C-03 §4/§5.1/§6 和 04 §2 的“按文件名保留”会让 `v999` 的旧库胜过 `v1` 的新库，也会使同秒不同 label、`-10` 与 `-2` 排错。按本次明确要求采用实际 UTC 时间及同秒生成顺序；反向版本、反向 label、12 次同秒调用均有真实测试。

4. **全新库定义。** open 已创建 schema_version 后文件大小非零，不能再仅以 stat 判断“新装空库”。按本次明确要求追踪是否本次创建以及是否有成功写入。已有空库保留起始 schema_version，全新库失败安全删除本次生成文件。

5. **04 §1 TODO-VERIFY(C-03) 的确切索引事实。** 无外键时同一事务 DELETE(id=1) 再 INSERT(id=1) 成功；两行 `UPDATE id=id+1` 也成功；2049 行同类 UPDATE 在 `id=2048` 报 Duplicate key。父行被外键引用后，更新父主键或删除父行均报 foreign key constraint。仍遵循业务禁止更新主键/UNIQUE 及不声明外键的红线；没有为此修改权威 DDL。

## 交接与复用经验

- 失败迁移后所有同路径句柄保持关闭；需要审计恢复结果时显式重新 open。该行为避免陈旧引擎状态/WAL 重放。
- write 内只读函数使用 tx；db.read 用于读取已提交快照，不应用来确认当前 write 刚写入的数据。
